### Refactoring

Starts with scouts: yes.

Translated from pstack `playbooks/refactoring.md`. Changed: the `how` skill → scouts. The `architect` skill → the **Architect** playbook in step 3. The refactoring-model subagent → a Paseo `worker`. The control skill → the repo's `verify-<app>` skill. The rebase → commits in order as each unit lands. The worker watches the pin pass on today's code before anything moves. You start on the PR branch before the first write, and the worker commits each green step as it lands. Not ported: `figure-it-out`.

**You own the contract. The structure changes. The behavior does not.** Distinct from Feature, which adds behavior, and Bug fix, which corrects it.

If the cleanup reveals a missing feature or a real bug, split it out and ship the structural change first against the pinned contract. A redesign is allowed, but name it and route to Feature. Large or cross-cutting structural work belongs to pstack's `figure-it-out`, which isn't ported: say so, and scope this run to one focused slice. This playbook is the focused-to-medium change.

1. Pin the behavior contract first. Start on the PR branch first, as **Opening a PR** step 2 says, so nothing lands on the base. Launch `scout` agents over the affected subsystem to learn the contract (see **Subagents** in the router). Then have a `worker` write a characterization test, snapshot, or equivalence harness that captures current behavior before any structure moves, and watch it pass on the current code. If the area has no coverage, write the pin before touching structure. Type check and lint are not a pin.
2. Name the structure the code is missing. Boring code stays when the shape is already clear and local. The reshape must delete branches or invalid states, not add indirection. Principle: **Model the Domain** (`principles/model-the-domain.md`).
3. Name the target shape. State what the module layout, types, and call graph should be if built today. When the target crosses a function boundary, run steps 1–3 of the **Architect** playbook (`playbooks/architect.md`) to pick the shape before the move, and add those steps to your todo list, copied in verbatim. Architect's step 3 hands back here, not to its step 4, and skips its scaffold commit. Steps 4–5 below write the code. When Architect ran, their workers take its synthesized sketch as their contract and report every deviation from it, as in Architect step 4. When the same kind of deviation keeps coming back, run Architect step 5. Principle: **Foundational Thinking** (`principles/foundational-thinking.md`). Principle: **Redesign From First Principles** (`principles/redesign-from-first-principles.md`).
4. Subtract before you add. Have a `worker` delete dead code, collapse one-caller wrappers, drop redundant validators, and remove orphan references before introducing the new shape. The smallest change that reaches the target shape ships. A speculative cleanup that "might help" gets reverted. Principle: **Subtract Before You Add** (`principles/subtract-before-you-add.md`). Principle: **Laziness Protocol** (`principles/laziness-protocol.md`).
5. Move in small behavior-preserving steps, each keeping the pin green. Have a `worker` commit each step once the pin is green, before the next starts, with the title and body you write in its handover. Check each commit with `git log`. For API reshapes, migrate every caller and delete the old API in the same wave. No compatibility shims, no parallel old-and-new paths. Spot-check every rename against the actual files. Renames silently miss usages in strings, prose, and back-references. Delegate the mechanical edits to a Paseo `worker` with a specific scope: file paths, the names being moved, the behavior to hold. Principle: **Migrate Callers Then Delete Legacy APIs** (`principles/migrate-callers-then-delete-legacy-apis.md`).
6. Prove behavior is unchanged on the real artifact, not "it compiles". For larger reshapes, run an equivalence check: a script that diffs old-vs-new outputs, a recorded baseline replayed against the new code, or a smoke run through the repo's `verify-<app>` skill. Principle: **Prove It Works** (`principles/prove-it-works.md`).
7. Confirm the change is worth keeping. The success measure is reduced reader load. If the diff does not lower reader load somewhere, have the `worker` revert it. Principle: **Minimize Reader Load** (`principles/minimize-reader-load.md`).
8. Keep the commits small and ordered: the subtraction, then the reshape, then any follow-on cleanup. Then run the **Opening a PR** playbook (`playbooks/opening-a-pr.md`), and add its steps to your todo list, copied in verbatim. Its step 2 is already done. Principle: **Sequence Verifiable Units** (`principles/sequence-verifiable-units.md`).

**Reply:** the structure that changed, the pin you held it against, the equivalence proof, the reader-load delta, what shipped and what got reverted. No new behavior.
