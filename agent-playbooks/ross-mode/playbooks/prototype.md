**You own the design decision, not the code. The prototype is a throwaway instrument. The real build follows Feature.**

The one playbook where the Laziness Protocol's "smallest change" and the verification bar invert. Speed over polish, code quality does not matter, no planning. The rigor is in picking the right design cheaply. Propose variations I didn't ask for, throw an approach away and try another.

1. Scope the decision the prototype exists to make: which layout, which interaction, which density, or for an empirical fork which behavior, timing, or approach. No decision means no prototype. Route to **Feature** (`playbooks/feature.md`).
2. Gather references when the design space is open. Search for prior art, summarize a moodboard of themes, palettes, and layouts, and let me pick directions before building. In an Autonomous run, pick them yourself and log the pick. For a visual decision, my installed design skills are references too: `design-taste-frontend`, `emil-design-eng`, `build-awwwards-quality-sites`, and `animate` for motion. Name each one you used. Skip this step when the direction is set. Principle: **Experience First** (`principles/experience-first.md`).
3. Have a `worker` build the throwaway (see **Subagents** in the router) in `/tmp/prototype-<slug>/`, outside the repo. For a visual decision, vanilla HTML/CSS/JS or the lightest stack that renders the idea, CDN deps, a dev server with hot reload. For a behavioral or timing decision, the smallest script that exercises the question. No production framework, no tests, no abstractions. Tell the worker this playbook inverts the Laziness Protocol, so speed beats polish. Have it leave the dev server running and report its URL.
4. When comparing alternatives, build them behind one switcher (buttons or a keypress), each variant labeled. Principle: **Exhaust the Design Space** (`principles/exhaust-the-design-space.md`).
5. Verify on the matching surface. For a visual decision, open the dev server with the Paseo browser tools, screenshot each variant, and drive the interaction. For a behavioral or timing decision, observe the thing you are deciding by logging the timing, printing the output, or watching the render. The observation is the test here, not an assertion. Principle: **Prove It Works** (`principles/prove-it-works.md`).
6. Present alternatives, tradeoffs, and a recommendation. The output is the decision plus the throwaway artifact, not shippable code. Hand the chosen direction to **Feature** (`playbooks/feature.md`) for the real build. Its step 2 picks the design and runs steps 1–3 of the **Architect** playbook (`playbooks/architect.md`) when the design crosses a function boundary. Principle: **Experience First** (`principles/experience-first.md`).

**Reply:** the variants explored, the evidence (screenshots for a visual decision, the observed output or timing for a behavioral one), tradeoffs, your recommendation, and the scratch path. Say plainly that the prototype is throwaway. When a plan will cite the prototype, have a `worker` copy its evidence out of `/tmp/prototype-<slug>/` into the plan's `media/` folder, because a reboot wipes `/tmp`. The scratch folder path plus the copied evidence stands in for a branch and a SHA.
