### Orchestrate

Starts with scouts: no.

Translated from pstack `playbooks/orchestrate.md`. Changed: the Topology and Supervision bullets → numbered steps. The program's state lives in the plan from **Multi-phase plan** (`playbooks/multi-phase-plan.md`) and the decision log, not a Project tracker. `Task` workers → Paseo agents, each owner in its own worktree. Owners stop at merge-ready and I merge, so a dependent PR starts after I merge its parent. The verifier on another model family → the plan's live lanes plus the **Interrogate** playbook, whose second seat runs on Codex. PR and CI event subscriptions → foreground waits and a Paseo heartbeat. Dropped: "call no scripts", cloud environments, Origin, retargeting, and sub-coordinators. Added: Orchestrate also sets the verdict as the commit status `ross-mode/verdict` with `scripts/verdict-status.sh`, and steps 8 and 9 cover a usage-limit stop, which waits for its reset and for the repo bot's `scripts/resume-after-limit.py`. No scouts, because the plan already holds what scouts would find.

Runs when I hand you a plan path from Multi-phase plan and say "run this plan", "orchestrate this", or "own this until it lands". With no plan, run Multi-phase plan first.

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.**

1. **Load the plan.** Read the plan file at the path I gave you. It's the tracker. A `worker` (see **Subagents** in the router) checks a box only when the evidence the box names exists, and you check that evidence first. Hand it every box a state change settles in one batch, not one launch per box. When `$PASEO_HOME/plans/<repo>/` isn't a repo yet, the worker runs `git init` there first. After each batch, the worker commits the plan file and its `media/` folder with a message that names the boxes it checked. Boxes already checked are done, so a rerun with the same plan resumes from the first unchecked box. Start the decision log (`practices/decision-log.md`) for the whole run. The first row records the plan path. Principle: **Make Operations Idempotent** (`principles/make-operations-idempotent.md`).
2. **Start with one unit.** Take the first PR section through owner, verdict, and merge-ready before you fan out, so a flaw in the owner's prompt costs one agent instead of every one. Principle: **Sequence Verifiable Units** (`principles/sequence-verifiable-units.md`).
3. **One owner per PR section.** Run `git fetch origin <base>`, then create its worktree with `create_workspace`, `isolation: "worktree"`, `mode: "branch-off"`, `branchName: "<type>/<short-slug>"`, and `baseBranch` the base's remote ref, such as `origin/main`. Launch the owner with `create_agent` in that worktree, with the Ross - Worker profile's provider, model, thinking, and features from `list_profiles`, but `modeId: "auto"` instead of its `bypassPermissions`. Start the owner's prompt with this line, word for word: `Load ross-mode first. Read ~/.claude/skills/ross-mode/SKILL.md in full and follow it as the /ross-mode skill for the task below, exactly as if Ross had typed /ross-mode, including its playbook choice and todo list.` Paseo wraps a prompt one agent sends another in a `<paseo-system>` envelope, so a leading slash command loads nothing. The explicit load doesn't arm `hooks/require-tasklist.sh`, which only a skill load registers. The owner keeps its todo list and no-write rule on its own. The worker install hook passes the owner, because the owner's prompt doesn't open with the Ross - Worker sentence. `auto`'s classifier vets each install instead. The prompt names the plan path, its PR section, and the program's issue, so it runs Feature or Bug fix through Opening a PR and **Babysit** `drive`, and stops at merge-ready. It also says that this worktree's branch is the branch for Opening a PR step 2 and this worktree is the one for Babysit step 1, so the owner creates no second branch or worktree. Opening a PR step 1 creates the PR's own issue with a `Part of #<program issue>` line. The owner waits for CI in the foreground, arms no heartbeat, and doesn't end its turn until merge-ready, or until it's blocked on a rebase or a call only I can make. A dependent PR's owner prompt gets the parent owner's final report pasted in full. The prompt also names the evidence that proves the work done, the paths it may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet. Owners launch their own agents, and those agents launch none. Only the owner's workers write its branch, and you never author or edit code. Principle: **Separate Before Serializing Shared State** (`principles/separate-before-serializing-shared-state.md`).
4. **Follow each section's `Depends on.` line.** A dependent PR starts only after I merge its parent. Nothing stacks.
5. **Verdict per PR, from agents that wrote none of its code.** At the merge-ready head, set `pending` with `~/.claude/skills/ross-mode/scripts/verdict-status.sh <pr> <head-sha> pending`, run from the PR repo's checkout, then launch the live lanes from the PR's **Verify, live** block and the perf probe from its **Verify, perf** block. Each is a Ross - Worker agent briefed to change no file and commit nothing. Each runs in its own worktree at the PR head (`create_workspace` with `mode: "checkout-pr"` and `prNumber: <n>`) and drives the surface per the plan's **Boot recipe**, on its own port when the boot recipe names one, in waves. Keep at most about ten agents you launched in flight, owners plus lanes, and size the lane waves to that cap. Each owner keeps at most about ten of its own. Archive each lane's workspace with `archive_workspace` once its report is in. Run the **Interrogate** playbook (`playbooks/interrogate.md`) on the diff. Principle: **Prove It Works** (`principles/prove-it-works.md`).
6. **Judge by the blocking rule.** Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has doesn't block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up. A trunk failure in the regression lane is recorded against trunk and doesn't block. Post `PASS`, `PASS+NOTES`, or `FAIL` with the head SHA on the PR with `~/.claude/skills/ross-mode/scripts/gh-post.sh comment <owner>/<repo> <pr> -`, with the verdict on stdin. It prints the comment's URL. Set the verdict at the same SHA with `~/.claude/skills/ross-mode/scripts/verdict-status.sh <pr> <head-sha> <verdict> <comment-url>`. Green CI and a review alone are not verdicts. A new head needs a fresh verdict, unless `git patch-id` at the verdict's SHA matches the current head. A new push leaves the new head with no `ross-mode/verdict` status. GitHub lists a required check as expected and doesn't list one that isn't required. The next verdict sets it. The script refuses a SHA that isn't the head, so a verdict at an old head can't label the new one. When the patch-id matches, or the new head changes only wording, set the last verdict at the new head with the old comment's URL. A one-lane re-verdict after a rebase or a minor fix also sets `pending`, then its result. If `ross-mode/verdict` isn't a required status check in the repo's branch protection or ruleset, suggest in the Reply that I make it one, so a merge waits for a passing verdict. Don't change it yourself. Required checks on a private repo need a paid GitHub plan. Send a `FAIL` back to the PR's owner with the findings.
7. **Supervise from the artifacts.** Read the diff, not the owner's summary. Check a PR's live state with `gh pr view` and `gh pr checks` before you report on it. Send back work that drifts from scope or grows past what was asked. Keep only the fixes that block the program, and park the rest as follow-ups. Account for every agent you launched as done, replaced, or absorbed into another agent's scope. Never relay messages or status between agents. Never message an agent to check on it, because `send_agent_prompt` restarts an idle agent. Principle: **Laziness Protocol** (`principles/laziness-protocol.md`).
8. **Replace a stalled agent by cause.** Judge an agent by its pushes and PR activity, not its status text. Retry by cause. A context limit gets a smaller scope, a dropped connection gets the same prompt, and a tool error gets a different seat. A usage limit gets no retry until its reset, then the same prompt, and never counts as one of the two retries. After two retries, drop the unit and replan around it. Log the drop and list it in the Reply. If the dropped unit blocks a dependent PR, that's a dead end for step 10. An install error is never fixed by installing. Report it. When a stopped agent returns late, check its result against the PR's current state, and hand any unique findings to a fresh agent. Principle: **Fix Root Causes** (`principles/fix-root-causes.md`).
9. **Wait without polling.** Wait for each agent you launched in the foreground, as **Subagents** in the router says. When an install reaches you as a `permission` request, deny it with `respond_to_permission`. Owners wait for their own CI, so only while the program waits on my merge of a parent, arm a Paseo heartbeat with the plan's heartbeat prompt, and delete it when that wait ends. For a run-wide usage-limit stop, rely on the repo bot's resume watcher, not a heartbeat. Its cron runs `~/.claude/skills/ross-mode/scripts/resume-after-limit.py`, which wakes the top coordinator after the reset (`scripts/resume-after-limit.md`). Log a row for each verdict, retry, drop, and heartbeat.
10. **Ask me only for a real decision.** That's a product or preference call, an irreversible action, or a dead end that survived a replan. Retries, CI flakes, review triage, and "should I keep going" never reach me. A rebase is mine to decide, because it needs a force-push, so the owner reports it per Babysit and you pass it on. Principle: **Never Block on the Human** (`principles/never-block-on-the-human.md`).
11. **Stop when every PR section is settled.** Each one is merge-ready with a clean verdict, dropped, or waiting on my merge of its parent. Before your reply, check the log and get the trail reviewed, as `practices/decision-log.md` says.

**Reply:** each PR's state and verdict with its link, what waits on my merge, what was dropped and why, and the decisions waiting on me.
